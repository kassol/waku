# 子会话生命周期与双向决策规格

## Problem Statement

用户希望通过主会话管理目标、进度和交付。子会话承担上下文分担与并行执行；工作区清理后仍留在日常会话列表、需要用户进入其中处理问题，会把内部执行细节持续转移给用户。仅有任务派发和完成通知，也无法处理子会话执行中需要决定、父会话正在等待结果的情况。

规格提出时，工作区清理与会话保留相互独立，删除会话会删除历史，管理接口缺少授权内代决与归档闭环。实施中确认工作区轻量投影和详情显示会丢失实际位置，已按持久执行工作区修复；不能把界面曾显示 main 当作 Git 自动切换分支的证据。当前实现和验证结果见[生命周期验收记录](waku-steward-child-lifecycle-acceptance.md)。

## Solution

以主会话作为日常交互入口。子会话作为临时执行单元，在主会话的任务详情中展示必要状态，完整过程按需展开。管家与子会话双向沟通：管家派发、反馈和作决定；子会话报告结果、阻塞和决策请求。子会话的问题统一交由直属管家处理，超出已有授权时由管家在主会话向用户提问。

双方通过持久请求和事件恢复推进。没有独立工作时进入明确等待，收到决定或成果后继续。管家接管结果、完成验收并可靠保存摘要和证据后，子会话归档隐藏，保留完整历史和追溯入口。Git 资源仍按独立安全条件清理。用户无需逐个查看、批准或清理子会话。

## User Stories

1. 作为用户，我希望日常会话列表以主会话为入口，以便专注目标和交付。
2. 作为用户，我希望在主会话查看正在执行的分工，以便了解必要进度。
3. 作为用户，我希望按需展开子会话详情，以便排查问题时仍有完整依据。
4. 作为用户，我希望管家派发前明确目标、范围和验收条件，以便减少执行中的重复确认。
5. 作为管家，我希望向直属子会话补充约束和反馈，以便执行过程能响应新的信息。
6. 作为子会话，我希望主动提出需要澄清的问题，以便避免自行猜测关键要求。
7. 作为子会话，我希望附上背景、方案和建议，以便管家有足够依据决定。
8. 作为子会话，我希望明确说明哪些工作受阻，以便等待只影响相关工作。
9. 作为子会话，我希望提出问题后进入等待决策状态，以便停止无效执行和轮询。
10. 作为管家，我希望等待成果时也能收到决策请求，以便解除子会话阻塞。
11. 作为管家，我希望忙碌期间的问题可靠保留，以便稍后处理且不遗漏。
12. 作为管家，我希望在已有授权内决定技术选择和操作，以便用户无需处理内部执行细节。
13. 作为用户，我希望新增范围、费用或权限需求回到主会话询问，以便保留决定权。
14. 作为用户，我希望问题说明原因、选项和影响，以便一次答复能解决实际阻塞。
15. 作为用户，我希望相关子会话等待我的答复时其他独立任务继续，以便保留并发效率。
16. 作为子会话，我希望收到与原问题对应的决定，以便准确恢复受阻工作。
17. 作为用户，我希望决定的接收状态可查，以便区分已受理、已接收和待核实。
18. 作为用户，我希望确认丢失时不会重复执行决定，以便避免重复副作用。
19. 作为用户，我希望取消或改方向后旧决定不会应用于新问题，以便保持执行一致。
20. 作为用户，我希望管家保留问题和决定摘要，以便事后理解成果形成原因。
21. 作为管家，我希望多个待处理问题按关联关系集中处理，以便减少重复询问。
22. 作为用户，我希望普通流式进度不反复唤醒管家，以便避免无变化协调。
23. 作为用户，我希望嵌套子会话的问题逐层转交，以便只面对主会话。
24. 作为用户，我希望 App 重启后恢复未完成请求和明确状态，以便不丢失等待事项。
25. 作为用户，我希望 App 退出期间停止自动开启新工作，以便保持正常退出的既有行为。
26. 作为管家，我希望区分一轮完成、任务待验收和生命周期完成，以便决定继续、返工或归档。
27. 作为管家，我希望确认成果与证据已接管后再归档，以便保留可靠交付依据。
28. 作为用户，我希望主会话留下子任务目标、结果、关键决定、验证及未解决事项摘要，以便快速理解交付。
29. 作为用户，我希望归档子会话退出日常列表但完整历史保留，以便界面简洁且过程可追溯。
30. 作为用户，我希望从摘要进入归档详情，以便查看必要的原始证据。
31. 作为用户，我希望归档详情默认只读，以便查看旧过程时不意外启动新工作。
32. 作为用户，我希望明确要求继续旧子任务时保留原记录并重新检查执行条件，以便安全返工。
33. 作为管家，我希望失败任务记录重试、替代或终止决定，以便失败也有清楚的收尾。
34. 作为用户，我希望未解决决策、待接收输入和活动执行阻止归档，以便工作不因隐藏而丢失。
35. 作为用户，我希望归档与工作区清理分别展示结果，以便知道哪些资源仍因安全原因保留。
36. 作为用户，我希望清理后显示原成果与清理状态，以便不会把已移除的工作区误当作仍可写入的位置。
37. 作为用户，我希望历史子会话保持可读且不被升级自动处理，以便已有工作不受影响。
38. 作为用户，我希望所有新增入口能通过键盘访问，以便保持原生操作体验。
39. 作为用户，我希望长历史和多项决策下界面仍流畅，以便随时询问进度或加入想法。
40. 作为用户，我希望整个流程通过隔离验收，以便日用 Steward 和原版 Waku 的会话不受测试影响。

## Implementation Decisions

- 遵循 ADR 0005：主会话统一交互，子会话临时执行、归档隐藏、保留完整历史，管家在已有授权内代决。直属管理范围及父会话权限上限继续有效。
- 扩展现有会话、管家管理、持久等待、输入投递、原生 driver、历史存储和任务视图；优先复用现有请求响应、事件及保存设施。归档具有独立的持久状态，不能复用会删除历史的删除操作，也不能仅通过侧栏过滤模拟完成。
- 决策请求保存稳定标识、来源子会话及所属管家、关联执行上下文、问题背景、方案建议、受阻范围、处理结果及接收状态。概念状态覆盖待管家处理、待用户决定、决定待接收、已解决、失败、取消或失效；具体协议字段在实施时按现有规范确定。
- 子会话仅能向自己的直属管家提出问题。管家仅能处理已授权的直属请求；嵌套子会话逐层转交，最终需要用户的事项关联原请求回到主会话。不得通过新的请求或回答接口访问兄弟会话、其他项目或提升权限。
- 普通澄清和原生权限审批沿各自真实接口处理。原生审批/提问沿用 harness 请求标识和响应语义；普通 prompt 或 steer 不可冒充审批回答。支持能力、请求存活状态及权限边界在回答前重新验证。
- 管家代决依据用户目标及已有授权；授权依据须能关联用户指令或既有权限记录，子会话输出仅作为待处理信息，不构成授权。“管家同意”本身不构成新增权限。没有足够授权依据时转交主会话，缺少可用原生能力时保留阻塞及原因，不伪造批准或恢复成功。登录、系统许可等必须由用户完成的动作仍由主会话说明并交接。
- 决策请求和响应先持久保存，再通知或投递；同一标识同一内容可查询或重试，同标识内容冲突拒绝。受理、原生接收与执行结果分别表示，无法确认是否送达时不自动重发。
- 决策事件能唤醒正在等待子任务成果的管家。处理决策后仍保留或恢复必要的成果等待，不能消费掉最终完成通知；用户改方向、取消和旧请求失效按关联上下文处理。管家忙碌时排队交接，避免并发启动相互冲突的父轮。
- 没有独立工作时释放模型执行轮并登记等待；原生审批或提问要求挂起请求存活时，保留该 harness 等待，不要求关闭其进程。完成和需要决定的事件触发协调，普通进度不触发无变化轮询。退出期间不自动启动新工作。
- 主会话显示相关工作状态、待用户事项和简明摘要；活动子会话集中在任务详情，归档项通过摘要追溯。用户仍可即时交流或明确提交新意见；内部 JSON、控制标记及重复完整子转录不进入主会话正文。
- 摘要关联源子会话及成果版本，包含任务目标、结果、关键决定、验证证据、未解决事项和资源保留原因；缺失信息明确标示，不能将“已完成一轮”或“空闲”推断为通过验收。完整原文按需加载。
- 生命周期结束要求管家明确接管结果并完成必要验收或终止处理、摘要与证据可靠保存、没有活动执行和未解决请求或未完成投递。多层任务按相同规则由直属管家接管；尚有未处理后代工作时不能结束上层生命周期。
- 收尾保存与归档必须可恢复。保存失败时保留可见任务及原因；重试或重启不能重复摘要、遗漏成果或将未收尾子会话隐藏。仅查看归档不启动 runtime、切换分支或重新创建工作区。
- 明确继续归档子任务时重新验证授权、任务关系及工作区条件。旧工作区已清理时禁止静默回退到原检出执行，沿现有创建能力重新委派并关联旧摘要；工作区仍有效时可显式恢复，保留旧完成记录。已交付任务仍遵循原有不可追加子任务边界。
- 会话归档与 Git 清理分别判断。保留原有资源归属、活动使用者、脏目录、未跟踪文件及持久成果引用检查；资源未能清理时说明原因，不能为了归档强删。清理后的详情保留原分支和成果信息并明确资源已移除。
- 升级不自动归档或删除旧子会话。本轮自动收尾用于新机制下明确接管的子任务；历史批量整理不纳入本规格。
- 持久化及共享协议向旧记录提供兼容默认值，并同步桌面与共享客户端的状态投影。耗时 Git、历史查询和文件操作运行于后台；渲染读取内存快照，完整归档按需加载。新增控件支持键盘、可见焦点和清晰状态文本。

## Testing Decisions

- 用户已确认沿用 MCP／daemon 公共接口作为主要自动化边界，复用真实 socket、临时 Git/SQLite 和可控 provider；新增能力尽量通过该边界检验，不另建内部测试专用接口。检查公开状态、收到的真实输入、实际文件/提交和可读历史，不以内部调用次数代替外部行为。
- 复用现有持久输入、管家等待、即时交流、组合协作、工作区清理及历史重开回归设施，覆盖管家协调、归档持久化、权限路由和客户端状态投影。
- 在同一受控任务走通：派发两个独立子任务，其中一个请求决定，父轮已结束等待；请求唤醒管家，授权内决定经原生对应接口确认后子任务继续；另一请求升级主会话等待用户答复，其余工作继续；最终结果验收、摘要保存、归档、资源清理和重开后追溯。
- 覆盖父轮忙碌、父子互等、多请求、嵌套转交、决定与结果同时到达、改方向及取消。断言决定不丢失、不重复执行，处理问题后完成事件仍能推进任务。
- 覆盖重复标识、内容冲突、原请求过期、权限撤销、跨项目/非直属访问、确认丢失、断连、重启和退出。检查不确定状态可查询，未确认决定不被自动重发，退出不启动新工作。
- 在实际原生审批/回答接口边界验证代决权限、用户转交和拒绝；不可用能力保留阻塞。补充 Claude、Codex 两种真实 harness 的隔离兼容验证，复用既有认证、新建临时任务，不把真实模型用于替代可控竞态检查。
- 归档检查包括保存失败、重复收尾、失败终止、返工、活动执行、未处理后代及待接收输入。归档前后逐项核对摘要、完整历史、成果及决策关联；查看详情不启动工作，恢复不写入已清理路径或未经选择的原检出。
- Git 清理继续验证未整合、脏目录、共享工作区、活动引用和持久成果保护。原检出、无关资源和既有历史保持不变；升级旧记录不会被自动归档。
- 独立签名 Debug App 后台验收主会话进度、请求决定、用户回答、恢复、摘要与归档详情，以及键盘焦点和长历史响应性。测试不得控制、替换日用 Steward 或原版 Waku，不抢占用户桌面焦点。
- 以受控记录确认等待期间无模型轮询、普通进度不重复唤醒、无意外重复决策或重复摘要；保留必要独立评审及整体验收，不承诺未经测量的模型费用或时延降幅。完成相关协议、类型和回归检查以及 Standards / Spec 复核。

## Out of Scope

- 自动批准所有请求、扩大权限、替代用户登录或系统许可、绕过原生审批。
- 永久删除子会话历史、升级时批量归档历史子会话或清理历史遗留工作树。
- 通用多代理聊天系统、固定阶段流水线、定时任务、退出 App 后继续运行。
- 新增或替换 provider、改造原生 harness 内部 subagent。
- 自动推送任务成果、部署、强制合并或覆盖用户未提交改动。
- 全量移动端交互重做、成本监控面板及无关 UI 重构。
- 本次规格发布不包含功能实现、安装或纵向任务发布。

## Further Notes

本规格综合 2026-09-07 已确认的子会话分层、归档保留、授权内代决及双向等待决策。现有已交付的协作功能作为基础；本规格实施后替代旧规格中要求用户进入子会话处理审批/提问的交互约定，完整历史保留及直属权限边界继续有效。

实现阶段核对两种 harness 的真实能力和请求恢复语义，所有“已接收”“已恢复”“已归档”结论均需要公共状态与实际行为证据。本规格发布为 ready-for-agent，随后按独立可验收的行为拆票并声明依赖；实施 subagents 使用 Astra。
