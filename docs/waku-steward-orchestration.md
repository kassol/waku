# 管家协作与任务收尾澄清

2026-09-06。本文保留实现前的设计澄清。规格为 [Issue #13](https://github.com/kassol/waku/issues/13)，仓库副本见[协作规格](waku-steward-orchestration-spec.md)。后续用户已授权实现 #14–#22；当前交付状态见[项目交接](waku-project-handoff.md)。

## 已确认方向

- 用户要求 `waku_prompt` 优先使用 harness 的 steer；不支持 steer 时使用反馈排队。提交不确定与明确不支持必须区分，不能在可能已经送达后自动重复投递。
- 用户选择独立即时交流入口：读取当前任务记录回答；仅在明确要求改变计划时，向执行中的管家投递。执行与交流应可同时进行。
- 用户选择任务集成分支：子分支汇入本次任务的集成分支，整体验收后按已有授权交付目标分支。
- 用户选择安全检查通过后自动清理：确认改动已保留、工作区干净且无人使用，再清理本任务资源；保留会话与提交记录。完成会话不等于已经整合成果。
- 任务集成分支从当前选中分支的已提交版本创建，最终按已有授权交付回该分支；不自动带入或处理未提交改动。子任务按依赖从合适的集成提交派生。
- 编排采用动态分工加必要检查：明确依赖与负责人、同一工作区单写入者、验收后整合和安全清理。按任务选择步骤，不要求所有任务套用固定阶段。
- 用户明确要求改方向时，优先 steer 受影响任务，无关任务继续；无法及时接收且继续会造成冲突时暂停相关任务。
- 即时交流仅读取任务记录并标出记录时间。讨论想法不改变执行；用户明确要求执行后，指令进入原任务，显示受理、送达、失败或待核实状态。

## 设计时的实现依据（历史）

- `crates/waku-core/src/steward.rs` 的后续输入入口拒绝开放轮次、忙碌状态及用户审批或回答等待。当前 `waku_prompt` 尚未接入 steer。
- `crates/waku-core/src/driver/codex.rs` 已发送带 `expectedTurnId` 的 `turn/steer`；`driver/claude.rs` 已支持轮中输入，写入成功后报告受理。受理不等于模型采纳。
- `src/app/runtime.rs` 的普通忙碌输入进入桌面队列，显式 steer 使用 driver；daemon 自动消费 MCP 反馈队列尚需设计。
- `crates/waku-core/src/creation.rs` 创建子 worktree 时未指定基线；inherit 可与父会话共用目录。未来清理必须核对实际资源使用关系。
- 现有持久等待在用户输入时撤销，见 `waku-steward-wait.md`。即时交流需要独立处理查询与执行指令，避免查询改变执行状态。

## 规格需落实的边界

- steer 的能力判断、投递标识、并发轮次切换、断连后的不确定状态，以及不支持 steer 时的持久排队。审批和用户问题仍由用户处理。
- 即时交流读取范围及与原任务的指令关联，不提升既有权限，不因只读查询撤销执行等待；用户改变方向与完成回调必须协调处理。
- 按明确提交验收与整合，结果记录包含起点、负责人、成果提交、验证证据和整合目标；避免多人修改共享目录及重复整合。
- 用任务名与状态说明待整合、已整合和可清理资源。清理核查共享目录、运行中使用者及成果保留，不因会话结束直接删除目录。
- 以可运行回归验证投递、等待与用户介入、整合和清理边界；减少重复查询与重复验收，保留独立评审。
