# 管家协作：即时交流、可靠输入与任务成果整合

## Problem Statement

用户委派长任务后，管家会长时间忙碌。普通输入排队到轮次结束，询问进度和补充想法都难以及时得到回应。当前管家工具拒绝向忙碌子会话发送输入，迫使管家取消执行再传递评审意见。反复查询相同结果、零散交接与重复验证增加了工作量。

子会话结束也不代表成果已整合。多个 worktree 和自动生成的分支缺少清晰的起点、负责人、交付目标与清理状态，用户难以判断哪些仍在使用、哪些已经交付。

## Solution

保留管家动态分工，增加可靠输入、独立即时交流和任务成果管理。运行中的子会话优先接收原生 steer，不支持时持久排队。管家完成当下协调后结束当前轮，由子会话事件继续唤醒。用户可同时了解进度和讨论想法，明确要求执行的指令才进入原任务。

一次代码任务使用独立任务集成分支，子任务按依赖承接已提交成果。管家集中验收、整合和交付，界面说明各项成果的状态。交付后仅自动清理已经确认安全的本任务资源，保留会话与提交记录。

## User Stories

1. 作为用户，我希望管家执行长任务时仍可即时交流，以便了解进度。
2. 作为用户，我希望交流答复注明所依据记录的时间，以便判断信息是否新鲜。
3. 作为用户，我希望讨论想法时执行继续，以便思考不会意外改变任务。
4. 作为用户，我希望明确要求执行的意见进入原任务，以便只有一份执行安排。
5. 作为用户，我希望看到指令受理、送达或待核实状态，以便知道意见是否传到。
6. 作为用户，我希望投递失败保留原文和原因，以便恢复处理。
7. 作为用户，我希望途中改方向只影响相关子任务，以便无关工作继续。
8. 作为用户，我希望必要时暂停相关执行，以便避免继续产生冲突。
9. 作为管家，我希望向正在运行的子会话 steer，以便及时纠正工作。
10. 作为管家，我希望不支持 steer 的执行环境自动排队，以便保留反馈。
11. 作为管家，我希望空闲子会话直接开始后续轮，以便保持原有输入行为。
12. 作为用户，我希望排队输入重启后仍存在，以便不丢失意见。
13. 作为用户，我希望重复请求不会重复执行指令，以便避免重复修改。
14. 作为管家，我希望提交结果不确定时可以查询，以便不靠重发猜测是否成功。
15. 作为用户，我希望输入不跨越任务或权限边界，以便其他会话保持独立。
16. 作为用户，我希望权限审批和用户问题由本人处理，以便保持决定权。
17. 作为管家，我希望等待子会话时结束当前轮，以便避免持续轮询。
18. 作为用户，我希望询问进度不撤销等待通知，以便工作随后仍能自动继续。
19. 作为用户，我希望回调与新指令协调处理，以便旧计划不会覆盖新要求。
20. 作为管家，我希望一次读取集中呈现可处理的子会话结果，以便减少重复交接。
21. 作为管家，我希望任务明确负责人和依赖，以便只启动具备条件的工作。
22. 作为用户，我希望分工适应任务规模，以便小任务不承担固定流程负担。
23. 作为管家，我希望同一工作区只有一个受管理的写入者，以便避免并发覆盖。
24. 作为管家，我希望评审绑定明确的成果提交，以便意见与代码版本一致。
25. 作为管家，我希望同批评审意见集中传递，以便减少反复中断。
26. 作为管家，我希望同版本验证证据可以共享，以便减少重复检查。
27. 作为用户，我希望独立评审和必要端到端验收保留，以便效率改进不牺牲正确性。
28. 作为用户，我希望任务从当前选中分支的已提交版本开始，以便起点符合我的工作上下文。
29. 作为用户，我希望未提交改动保持原位，以便当前工作不被带入或覆盖。
30. 作为管家，我希望子任务从其依赖已经整合的提交创建，以便不重复手工同步基础改动。
31. 作为用户，我希望看到任务名称、工作分支和整合目标，以便理解分支用途。
32. 作为管家，我希望先汇入任务集成分支再整体验收，以便发现组合后的问题。
33. 作为用户，我希望任务最终按已有授权交付回选中分支，以便保持明确的交付边界。
34. 作为用户，我希望分支冲突或目标移动时保留现场并说明原因，以便避免覆盖新工作。
35. 作为用户，我希望区分执行完成、待整合、已整合和可清理，以便准确判断交付状态。
36. 作为用户，我希望安全检查通过后自动清理本任务 worktree 和分支，以便减少残留。
37. 作为用户，我希望脏目录、共享目录和仍在使用的资源得到保留，以便清理不伤及工作。
38. 作为用户，我希望清理后仍能查看会话、成果提交和验证记录，以便追溯交付。
39. 作为用户，我希望清理中断或失败后可以安全重试，以便不会误删其他资源。
40. 作为用户，我希望更新与测试使用独立 App 和临时工作区，以便日用 Steward 和原版 Waku 不受干扰。

## Implementation Decisions

- 复用现有管家 MCP、daemon 会话控制、provider driver、持久会话历史和工作区操作边界。可靠投递、等待和资源状态由 daemon 管理；UI 读取状态，管家决定分工。避免另建通用流水线引擎。
- 扩展 `waku_prompt`：空闲时提交后续轮；运行中且支持 steer 时向当前轮投递；明确不支持时持久排队。轮次切换后重新核对状态。权限审批和用户问题保持独立，不以普通输入代答。
- 投递具备持久标识，重试绑定调用者、目标与相同内容；相同标识不同内容拒绝。返回实际投递方式、目标轮次及状态。区分 daemon 已受理、provider 已确认接收、排队、失败和结果不确定；不把接收显示成模型采纳。兼容现有空闲提交的轮次返回语义。
- Codex 复用原生轮次匹配与 steer 确认；Claude 复用现有轮中输入，明确确认层级仅到传输接收。部分写入、断连或确认丢失时保留待核实状态，不能自动降级排队或重发可能已送达的内容。
- 排队内容由 daemon 持久保存并按受理顺序消费，不依赖桌面保持连接。仅在允许新输入的状态提交；等待用户处理期间不自动绕过等待。提交前保存状态，重启不重发提交结果不确定的输入。每次投递与查询重新检查调用者权限及任务关系。
- 即时交流使用独立会话执行上下文，与正在执行的管家并行。入口关联原任务，仅读取经过范围限制的任务记录与结果摘要，显示记录时间与缺失信息；不以轮询执行模型获取进度，不承诺尚未产生的信息。
- 即时交流默认无工作区写入、命令执行、权限代答或子任务控制能力；该限制须由执行边界保证。讨论内容与执行指令分开记录。用户明确要求执行时，通过用户授权的入口将指令关联到原任务，展示投递状态。该入口不能成为管家 MCP 访问兄弟或无关会话的途径。
- 即时交流查询不改变原任务轮次、队列或持久等待。执行指令与完成回调在原任务边界串行，保留尚待处理的子任务结果。新计划接管后重新建立仍需要的等待，不能继续用旧等待重复推进旧计划。
- 用户变更优先 steer 相关任务，无关任务继续。无法及时接收且继续会造成冲突时暂停相关任务；等待实际停止确认，不将受理取消等同于停止。反馈采用集中交接，紧急纠错可提前投递。
- 编排指导要求声明负责人、依赖、工作范围、基线和验收结果；长时间实现或验证优先委派。管家有独立工作时执行，否则登记等待并结束当前轮。可同时处理的完成通知集中读取；新结果、失败或用户介入才推进协调。
- 依赖完成条件是所需成果已验收并整合到明确提交，不能仅凭子会话空闲启动后继任务。受管理的写入任务不得并发占用同一实际工作区；共享继承目录必须核对使用关系。外部进程不在调度器控制范围，整合和清理前仍核查实际 Git 状态。
- 独立评审以固定成果提交为依据，集中反馈后由明确负责人修改。测试证据关联提交、检查内容和运行环境；只有适用范围及版本一致才复用，代码变化后重验受影响检查。保留必要的整体验收。
- 每次代码任务记录选中目标分支及起点提交，创建独立任务集成分支；默认起点是该分支当时的已提交版本。未提交改动不自动提交、暂存、搬移或清除。非 Git 任务继续使用已有工作目录能力，不强行创建分支。
- 子任务从满足依赖的集成提交派生独立 worktree。分支使用项目约定前缀、短任务名称和防冲突标识，界面优先显示任务名，提供起点、工作分支、负责人及整合目标。
- 记录成果提交、验收证据与整合结果；重复整合请求先核查已完成状态。交付前核对目标分支变化；存在冲突、未提交改动或目标正在被使用时，不重置或覆盖，保留现场供管家按已有授权协调处理。推送和发布仍遵循项目授权，整合成功不等于已经部署。
- 将执行状态与成果状态分开表达，支持待整合、已整合和可清理。状态入口位于任务与分支的关联位置，避免在页面空白处独立摆放提示。沿用原生键盘操作、焦点与可访问性规范。
- 清理前检查本任务资源归属、共享引用、运行中使用者、工作区含未跟踪文件的干净状态，以及成果已保留在交付记录对应的持久 Git 引用中。仅删除满足条件的本任务 worktree 与分支，不使用强制删除、不清理无关工作区。任务集成资源满足同样条件后才清理。
- 清理失败逐项记录，重试重新核查条件；历史与成果记录保留，不能将删除会话等同于清理工作区。既有任务不自动补建集成分支，不批量清理历史遗留 worktree。
- 持久结构沿用既有数据库迁移和协议版本机制，兼容旧会话读取；操作标识、任务关系、成果与资源状态须在重启后可恢复。耗时 Git、文件与数据库工作运行于后台，渲染只读取内存状态。

## Testing Decisions

- 用户已确认主要自动化边界为现有 MCP／daemon 公共接口。复用真实 socket、临时 Git、临时数据库与可控 provider 的创建、查询、等待和恢复测试设施；断言外部返回、可读历史、实际 Git 状态及 provider 收到的输入，不以内部函数调用次数替代行为验证。
- 核心闭环：创建任务与两个有依赖的子任务，轮中投递反馈，管家结束轮次等待，用户即时查询保持等待，子任务完成唤醒，按指定提交验收整合并安全清理，重开后可追溯成果。尽量通过同一公共边界覆盖完整流程。
- 投递矩阵覆盖空闲、支持 steer、明确不支持、等待用户、轮次切换、重复请求、内容冲突、确认丢失、断连和重启。检查输入无静默丢失，可能已经提交的输入不自动重发，权限撤销后拒绝继续操作。
- 并发检查覆盖用户改计划与子任务完成同时发生、管家尚未结束、多个结果同时到达、取消尚未确认，以及关闭 App 时禁止自动启动新工作；查询进度不得撤销等待。
- Git 检查使用临时仓库，覆盖依赖基线、共享目录写入冲突、重复整合、目标分支移动、合并冲突、脏目录及未跟踪文件、活动引用、已整合和未整合分支、清理失败重试。断言原检出及非本任务资源保持不变。
- 即时交流通过其受限执行入口验证读取范围和命令拒绝；用户明确交付指令后，再验证原任务的投递记录。摘要不足时须显示未知，不能借扩大权限获取信息。
- 两种真实 harness 补充隔离兼容性验证，检查原生接收与轮次行为；使用现有配置与临时任务，避免用真实模型代替可控竞态测试。
- 新即时交流与成果状态在独立签名测试 App 中走通后台交互验收：执行继续时提问、讨论不改计划、明确变更后查看送达状态、查看整合与清理状态、清理后查看历史；同时验证键盘操作和长任务下的响应性。不得控制或替换用户正在使用的 App。
- 效率验证使用相同受控任务比较无变化查询次数、重复结果读取、为传递反馈而发生的取消及重复验证；不承诺未经测量的耗时或模型费用降幅。完成仓库要求的类型、协议及相关回归检查后停止无目的扩测。

## Out of Scope

- 固定阶段流水线、通用定时调度、退出 App 后继续执行及更换原生 harness。
- 新增 provider、代替用户审批、扩大管家对非直属会话的管理权限。
- 未授权推送、自动部署、强制覆盖目标分支、自动处理用户未提交改动。
- 自动清理历史遗留分支和 worktree，迁移或删除原版 Waku 数据。
- 全面成本监控面板、模型速度保证及与本任务无关的 UI 重构。
- 本规格发布不包含功能实现、安装或纵向任务发布。

## Further Notes

本规格综合 2026-09-06 的实际任务复盘与用户确认的设计。此前已实现的持久等待回调作为基础，本规格补齐输入、交流和成果生命周期。独立测试与日用 App 隔离、用户历史保留、管家仅管理直属子会话及正常退出停止任务的既有约定继续有效。

发布时标记 ready-for-agent；后续按可独立验收的用户行为拆分纵向任务并声明依赖。实现前以本规格为整体合同，具体协议字段在实施时按现有项目规范确定。
