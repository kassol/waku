# 上游同步流程与记录

本项目与 `egoist/waku` 可以沿不同产品方向发展。同步以本项目需求、架构和行为约定为准，逐项吸收有价值的改动。禁止直接机械合并上游分支。上游仅用于读取；所有开发提交只推送 `origin`（`kassol/waku`）。

## 执行流程

1. 读取本文件最近完成的上游 SHA 和尚未解决的延期项，核对项目规范、设计与工作区状态。
2. 从 `upstream` 获取更新，确定目标分支，将本轮目标固定为完整 commit SHA。记录起点与目标；验证起点是目标的祖先。上游改写历史时先重建比较范围，并记录依据。
3. 审查起点到目标的提交及实际源码，按行为和依赖关系归组。每组记录上游提交、解决的问题、本地相关实现、采纳方式和理由：采纳、适配、跳过或延期。保留本项目产品决策、原版 App 隔离及协议边界。影响范围或对外行为的新决策由用户确认。
4. 按已确认结论移植或改写必要部分，检查关联调用、数据迁移和本地已有功能。执行项目要求的检查及最小有效回归验证；测试 App 启动前必须满足隔离约束。
5. 完整范围均已评估、所采纳改动验证通过后，追加完成记录，与改动一起提交并推送 `origin`。此时才把本轮目标 SHA 作为下一轮起点。即使全部跳过，也记录范围和理由。

完成记录包含：日期、起点完整 SHA、目标完整 SHA、各组上游提交与处理结论、验证结果、延期项及重审条件。承载记录的 Git 提交定位本地改动，无需在提交内填写自身 SHA。

“已审查至”表示该范围的每项变更都有处理结论，允许明确跳过或延期。下轮同时检查新范围和未解决延期项，避免遗漏。中断时记录目标、已处理范围与剩余工作，保留上一完成基线；恢复后完成本轮再推进。
